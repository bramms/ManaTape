# Робота над Mana Tape

Почніть із [README](README.md) і [карти документації](docs/index.md). Перед зміною поведінки прочитайте [DESIGN](docs/DESIGN.md), потім [ARCHITECTURE](docs/ARCHITECTURE.md). Для конкретної задачі відкрийте потрібні розділи: [конфігурація](docs/CONFIGURATION.md), [робота з панеллю](docs/USAGE.md), [експлуатація](docs/OPERATIONS.md), [дані моделей](docs/BENCHMARKS.md), [розробка](CONTRIBUTING.md), [підтримка](docs/MAINTENANCE.md), [безпека](SECURITY.md) або README відповідної інтеграції.

Явні інструкції користувача мають перевагу над домовленостями цих файлів. DESIGN задає прийняті принципи продукту й інтерфейсу, ARCHITECTURE — межі та гарантії реалізації. Код показує фактичну поведінку; розбіжність із каноном може бути дефектом, а не новою вимогою. [VALIDATION](docs/VALIDATION.md) — датований звіт, а не підтвердження поточної версії чи заміна вимог.

Змінюючи поведінку, оновіть відповідний канонічний документ у тій самій зміні; не дублюйте його в інших файлах. Виправлення дефекту не потребує переписування правильної вимоги. Не створюйте окремих копій канону для конкретного AI-провайдера, моделі чи середовища агента: достатньо посилання на цей вхід.

- Проєкти OMP зовнішні. Код не повинен залежати від конкретного користувача, хоста, набору ролей або каталогу встановлення. Особливості інсталяції — у приватній конфігурації.
- Ніколи не зупиняйте й не перезапускайте OMP або його воркери. За потреби перезапускається лише Mana Tape.
- Перевіряйте записи лише на одноразових fixtures. Не очищуйте відкриту вкладку користувача з чернетками.
- Зберігайте ревізії, чернетки, коментарі YAML, резервні копії та відновлення транзакцій. Не обходьте конфлікти.
- Невідоме, застаріле, FREE та вичерпане — різні стани. Не вигадуйте даних або успішних перевірок. Немає ціни — не означає FREE.
- Не додавайте ключів, токенів, auth DB, native конфігурацій, приватних журналів чи резервних копій у Git. Перевіряйте staged-файли.
- Імена `forge` — сумісні внутрішні ідентифікатори. Не перейменовуйте їх без міграції.
- Використовуйте наявний стек. Нові залежності та узагальнення додавайте лише за конкретної потреби.
- Після змін коду запускайте `make test check`. Для інтеграції — її окремі тести. Для змін лише документації перевірте зміст, посилання й узгодженість. Мережеві inference-перевірки не входять у тести за замовчуванням.
- Після змін UI перевірте світлу/темну тему, 1440 або 1920, 1280, 390 і 320px; довгі/невідомі назви, порожній пошук, клавіатуру, drag/tap та Undo. Скріншот не доводить роботу подій. Записуйте фактично виконані перевірки.
- Зберігайте граматику CUT / CUTS / EDITION, читабельність, reduced motion, фокус і прокручування. Фонове оновлення не має анімувати монтаж.
- Не вигадуйте виконаних тестів, людського приймання чи незалежного рев’ю. Перевірка агентом не є перевіркою людиною. Записуйте спосіб, обсяг і межі фактичної перевірки.
- Не змінюйте видимість GitHub без явного запиту власника. Ліцензію основного проєкту має обрати власник.
